# LLM Release Behavior — Поведение агента в production

Документ описывает режимы работы агента, ограничения и degraded-поведение для защиты проекта.

## Режимы работы

### 1. Search (Поиск)
- **Триггер:** Пользователь хочет подобрать/купить конкретный инструмент, указывает бюджет, модель или стиль.
- **Пайплайн:** `detect_mode` → `_classify_query` → `extract_search_params` → `search_reverb` → `rank_results` → ответ с карточками.
- **Результат:** JSON со списком гитар (ссылки, цены, фото) из реального каталога Reverb.

### 2. Consultation (Консультация)
- **Триггер:** Теоретические вопросы ("что такое хамбакер?", "как дерево влияет на звук?").
- **Пайплайн:** `detect_mode` → `_handle_consultation` → LLM отвечает текстом.
- **Результат:** Markdown-текст с объяснением. **Поиск на Reverb НЕ вызывается.**

### 3. Clarification (Уточнение)
- **Триггер:** Запрос на поиск, но не хватает данных (нет бюджета или типа гитары).
- **Пайплайн:** `_classify_query` → `check_needs_clarification` → вопрос пользователю.
- **Результат:** Уточняющий вопрос, сессионное состояние сохраняется.

### 4. Off-topic (Не по теме)
- **Триггер:** Запрос не связан с гитарами/музыкой (программирование, погода, рецепты).
- **Пайплайн:** `detect_mode` → `off_topic` → фиксированный ответ `OFF_TOPIC_ANSWER`.
- **Результат:** Вежливый отказ. **LLM НЕ вызывается.**

## Что агент НЕ должен делать (антигаллюцинации)

1. **Не выдумывать цены** — все цены берутся только из API Reverb.
2. **Не выдумывать ссылки** — все URL берутся только из `search_reverb`. Consultation-ответы фильтруются через `_sanitize_consultation_answer` (блокирует URL, упоминания магазинов, списки моделей с ценами).
3. **Не проверять продавцов** — агент не оценивает репутацию продавцов.
4. **Не обсуждать доставку/оплату** — явный запрет в `AGENT_PROMPT.md`.
5. **Не генерировать JSON в consultation** — режим консультации возвращает только текст.

## Degraded Mode (работа без внешних сервисов)

### Без `GROQ_API_KEY`
- `create_llm_client()` возвращает `None`.
- **Consultation:** Фиксированный ответ "сервис временно недоступен (API ключ не настроен)".
- **Search:** Fallback — текст запроса используется как `search_queries`, поиск на Reverb всё равно выполняется.
- **Off-topic:** Работает без LLM (паттерны в `mode_detector.py`).

### С `USE_MOCK_REVERB=true`
- `search_reverb` возвращает mock-данные вместо реальных запросов к Reverb API.
- Ранжирование (`rank_results`) работает нормально на mock-данных.
- Используется в тестах для изоляции от внешних API.

### Когда LLM вернул невалидный JSON
- `extract_params_from_llm_response` → fallback `{search_queries: [], price_min: None, price_max: None}`.
- Clarification спросит недостающие данные.

### Когда Reverb вернул 0 результатов
- `_build_relaxed_queries` пробует ослабленный запрос (например, убирает бренд).
- Если всё ещё 0 — возвращается пустой список `results: []`.

## Честные ограничения

1. **Качество маппинга зависит от LLM** — без `GROQ_API_KEY` маппинг абстракций в технические параметры не работает. Fallback использует текст запроса напрямую.
2. **Reverb API может быть недоступен** — при проблемах с сетью поиск возвращает ошибку.
3. **Суммаризация длинных диалогов** — `context_manager` суммаризирует историю при превышении 75% лимита токенов, но качество суммаризации зависит от LLM.
4. **Детектор режимов основан на паттернах** — edge-cases могут определяться неверно, но fallback на `consultation` безопаснее, чем ложный `search`.
